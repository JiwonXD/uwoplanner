# 항로 · 대항해시대 오리진 배치 플래너

별도 운영 서버 없이 GitHub Pages에서 실행하는 정적 웹 앱이다.
HTML/CSS/JavaScript와 모듈 Web Worker를 사용하며 외부 npm 패키지 없이 빌드한다.

## 실행

Node.js 22 이상:

```sh
npm test
npm run build
npm run dev
```

미리보기: http://127.0.0.1:4173
배포 파일: `dist/`. Python과 SQLite는 데이터 정리용이며 방문자에게 필요하지 않다.

## 기능

- 644명 항해사 검색, 타입·등급 필터, 상세 스탯·효과·기술 조회
- 최대 7척 × 11명 수동 배치, 배치와 장착 효과 잠금
- 일반 항해사 5개 / 제독 6개 효과 선택, 별도 3차 초월 효과 활성화
- 선단 공통 및 선박별 목표 레벨 설정
- Worker에서 시간 제한 탐색, 중지, 결과 검토·적용
- 보유 항해사 필터, 브라우저 저장, 배치 파일 내보내기·불러오기
- 보유 관리 체크리스트: 이름·직업 검색, 타입·등급 및 전체/보유/미보유 필터,
  검색 결과 일괄 보유 등록·해제, 즉시 저장
- 필수 포함: 항해사를 반드시 포함하되 선박과 장착 효과는 목표에 맞춰 자동 선택
- 입항 알림(`arrival.html`): 게임 창을 브라우저 화면 캡처로 받아 도착 로딩 화면을 감지하고
  알람음과 디스코드 웹훅으로 알림(탭 제목도 깜빡임)

필수 지정은 보유 관리와 별도 화면에서 보유 항해사만 선택한다. 보유 목록을 자동 변경하지 않는다.
목표 입력은 선단 효과(모험·교역), 선박 효과(전투), 해전 기술로 분리한다.
선박 효과·기술은 대상 선박을 먼저 정하며, 등록된 목표도 적용 범위와 종류별로 묶어 표시한다.
보유 해제 시 필수 지정과 배치 잠금도 해제된다.
보유만 계산을 켠 상태에서 미보유 잠금 항해사가 있으면 조용히 포함하지 않고 충돌을 알린다.
필수·잠금 항해사 합계가 선실 수를 넘으면 탐색 전에 오류를 표시한다.
필수 항해사의 실제 선택한 효과 기여분을 먼저 반영하고 남은 목표 부족분을 계산한다.
목표와 관계없는 필수 항해사도 제거하지 않는다. 필수 인물의 기여는 결과 설명에 표시한다.

10/30/50/70레벨 효과는 모두 같은 장착 후보이며 습득 레벨을 탐색 조건으로 제한하지 않는다.
동일 이름의 후보가 중복되면 가장 높은 보유 레벨 하나를 선택한다.
3차 초월 효과는 항해사 상세에서 완료로 체크한 경우에만 별도로 더한다.
배치 잠금은 해당 항해사의 위치와 장착 효과를 자동 탐색에서 고정한다.

자동 맞춤은 여러 번의 탐욕 탐색과 불필요 인원 제거를 수행한다. 목표 부족분을 먼저 줄이고,
선택한 스탯이 주스탯인 항해사 수 또는 적은 인원을 차순위로 평가한다.
주스탯 인원수가 같으면 조합 전체의 제독(S+), S, A, B, C 인원수를 순서대로 비교하며 높은 등급 인원이 많은 조합을 우선한다. 이를 위해 남은 선실도 채울 수 있다.
주스탯은 항해사별 가장 높은 수치의 스탯이며 공동 1위는 모두 포함한다. 수치가 없거나 모두 0이면 주스탯으로 세지 않는다. 최적해나 불가능 여부를 증명하지 않는다.
현재 스탯은 원본 수치의 단순 합계이며 성장/장비/선박 보정은 포함하지 않는다.
추천 배치는 선택한 주스탯 우선, 같은 조건이면 높은 등급 순으로 각 선박의 선실 1부터 순환 배치한다.
선박 효과·해전 기술 목표에 기여하는 항해사는 해당 선박에 유지하고, 나머지 인원을 선실 정원 안에서 분산한다.
장착 효과와 필수 항해사는 유지하며, 탐색 중간 결과와 최종 결과에 같은 배치 규칙을 적용한다.
태생·직업 직접 수치 보너스는 효과 레벨 목표와 합산하지 않는다.

## 입항 알림

`web/arrival.html`은 별도 서버 없이 브라우저 안에서만 동작한다. 화면 공유 API로 게임 창을 받고,
프레임을 Web Worker(`detect-worker.js`)로 보내 좌상단 제목 글자 블록을 찾는다.
타이머가 아니라 캡처 프레임 스트림을 그대로 소비하므로 탭이 뒤에 있어도 검사가 멈추지 않는다.

감지는 `detect.js`가 담당한다. 프레임의 좌상단 35%×30% 영역만 폭 최대 560px로 줄이고, 밝고 채도가 낮은
픽셀을 글자 마스크로 만든 뒤 `arrival-template.js`의 기준 마스크와 비교한다. 점수는
(글자 위치가 밝은 비율) − (글자 바깥 테두리가 밝은 비율) − (블록 안 나머지 자리가 밝은 비율)이며
배경 그림과 무관하다. 글자 정확 위치의 밝은 비율이 기준별 하한(도시 0.6, 마을 0.5) 미만이면
점수를 그 값으로 낮춘다. 밝기 기준도 기준별로 다르며(도시 215, 어두운 바 위의 마을 제목 200)
`build_arrival_template.py`의 `--luma`, `--sat`, `--exact` 옵션으로 저장한다.
배율 0.45~1.6을 탐색해 창 크기와 UI 배율이 달라도 찾는다. 도착 화면은 0.9 안팎,
다른 화면(세계지도, 항해)은 0.55 이하로 측정됐고 기본 임계값은 0.8이다. UI 배율 90~110%의
도시·마을 도착 화면 13장과 창 폭 960~1920 조합은 모두 0.83 이상이었다. 임계값을 넘는 프레임이 2회 연속이거나
임계값보다 0.03 이상 높은 프레임이 1회면 알리고, 같은 도착은 설정한 시간 동안 다시 알리지 않는다.

기준 마스크는 `scripts/build_arrival_template.py`로 만든다. 같은 크기의 도착 화면 스크린샷
여러 장에서 모두 흰색인 픽셀만 글자로 남기므로 배경이 다른 스크린샷일수록 좋다.
`--name`으로 장소별 기준을 따로 등록하며 알림에는 감지된 장소 이름이 표시된다.
현재 기준은 두 가지다. 도시는 "도시 / 입항 중입니다." 로딩 화면, 마을은 로딩 없이 바로 뜨는
마을 팝업의 "〈 마을 ?" 제목 블록이다. 스크린샷은 저장소에 넣지 않고 `data/arrival-samples/`(gitignore)에 둔다.

```powershell
python scripts/build_arrival_template.py --name 도시 --exact 0.6 입항1.png 입항2.png 입항3.png
python scripts/build_arrival_template.py --name 마을 --region 10,160,36,75 --luma 200 마을1.png 마을2.png 마을3.png
```

자원 사용: 캡처는 초당 2~3프레임만 받고 검사는 0.6초에 한 번이다. 한 번 찾은 배율을 기억해 다음 검사는
그 주변 배율만 보며(20회마다 전체 탐색), 실측 처리 시간은 전체 탐색 25~55ms, 배율 고정 시 약 15ms로
대기 중 CPU 사용은 한 코어의 5% 안팎이다.
`arrival.html?debug`로 열면 감지 기록과 스크린샷 테스트 도구가 보인다.
제약: 크롬·엣지 PC 기준이며 게임은 창 모드여야 한다. 최소화하면 프레임이 멈출 수 있어
10초 이상 프레임이 없으면 경고를 표시한다. 디스코드 웹훅 URL과 설정은 `localStorage`에만 저장한다.

## GitHub Pages 배포

1. 이 프로젝트를 배포할 GitHub 저장소에 올린다.
2. 저장소 Settings → Pages → Build and deployment → Source를 **GitHub Actions**로 선택한다.
3. `dev`에서 수정한 뒤 push한다. `Check changes`가 테스트와 빌드만 실행한다.
4. `dev` → `main` Pull Request를 생성한다. PR에서도 `Test and build` 검사가 실행된다.
5. 검사를 통과한 PR을 **Create a merge commit**으로 병합한다. `dev` 브랜치는 삭제하지 않는다.
6. 병합으로 `main`이 변경되면 `.github/workflows/pages.yml`이 테스트·빌드 후 운영 사이트에 자동 배포한다.

배포 워크플로는 `main` push에만 실행된다. `dev` push나 PR 생성만으로 운영 사이트가 바뀌지 않는다.
다음 작업을 시작하기 전 `git fetch origin` → `git switch dev` → `git merge origin/main`으로 병합 이력을 반영한다.

Settings → Branches에서 `main` 보호 규칙을 설정한다.
**Require a pull request before merging**, **Require status checks to pass before merging**를 켜고
필수 검사로 **Test and build**를 선택한다. **Do not allow bypassing the above settings**도 켜서 관리자에게 적용한다.
혼자 운영할 때는 다른 사람의 승인을 필수로 요구하지 않는다. 강제 push와 브랜치 삭제는 허용하지 않는다.
이 보호 규칙은 저장소 설정에서 별도로 적용해야 하며, 워크플로 파일만으로 직접 push를 막지는 못한다.

사용자 저장소의 `/uwoplanner/` 같은 하위 경로에서도 동작하도록 데이터·스크립트·Worker 경로를 상대 경로로 사용한다.
저장소: https://github.com/JiwonXD/uwoplanner
Pages 주소: https://uwoplanner.com/
배포 상태는 저장소 Actions의 `Deploy GitHub Pages` 작업에서 확인할 수 있다.
데이터를 갱신한 뒤에는 빌드를 다시 수행한다. 공개 배포에는 `dist/`만 업로드하므로
원본 수집 스크립트와 SQLite 파일은 웹 배포물에 포함되지 않는다.

### 선박별 선실 정원

각 선박의 선실 수는 기본 11개이며 1~최대값 범위에서 설정합니다. 최대값은 `web/model.js`의 `MAX_CABINS`에서 관리하며, 이 값을 올리면 화면과 자동 배치의 상한도 함께 변경됩니다. 기존 저장 파일의 선실 정원과 배치는 유지하고 내부 배열만 새 최대값까지 확장합니다.
